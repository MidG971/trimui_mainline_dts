# Session 2026-09-11 — THS/fan verified, LED indicator, display root-cause

## P3/P4 — THS thermal sensors + pwm-fan cooling: HW-VERIFIED

The A523 THS driver (patches `0021-0023`, compatibles `sun55i-a523-ths` /
`-ths-ddr`) and the `trimui-thermal.dtsi` sensor/zone/fan-map definitions are
now confirmed working on hardware. Live idle temperatures (device on battery,
cold boot):

| Zone | Sensor | Idle |
|------|--------|------|
| cpub-thermal | ths 0 (big cluster) | 37.4 °C |
| cpul-thermal | ths 1 (little cluster) | 37.8 °C |
| gpu-thermal  | ths 2 | 38.6 °C |
| npu-thermal  | ths 3 | 38.6 °C |
| ddr-thermal  | ths_ddr | 37.8 °C |

- **Calibration is correct** (sane ~37-39 °C, not garbage).
- **The `0023` NPU-channel guard is confirmed** — gpu/npu read a real ~38 °C,
  not the false 183 °C that would otherwise trip the 110 °C critical shutdown.
- **`pwm-fan` is now temperature-controlled** (cooling-map on cpul/cpub at
  90 °C, `step_wise` governor) instead of running pinned. At a cool idle its
  cooling state is 0.
- Module built with the **local laptop build tree** (`v7.2-rc3`, vermagic
  `7.2.0-rc3-dirty` — matches the running kernel), test-loaded clean, deployed.

### Deploy method (important for reproducibility)
The board DTS in this repo does **not** currently reproduce the *deployed*
(display-bring-up) DTB — the deployed DTB carries the DE33 `display-engine`
pipeline and other nodes that the repo board DTS lacks. So rather than rebuild
the whole DTB from the repo (which would risk regressing the display), the THS
nodes were injected **surgically** into the deployed DTB (decompile → append the
`trimui-thermal.dtsi` nodes via dtc path-reference syntax → recompile), leaving
everything else byte-identical. `trimui-thermal.dtsi` remains the source of
record; it is ready to `#include` from the board DTS once the board DTS and the
deployed display DTB are reconciled (see the display plan below).

## LED ring — power-on indicator (`userspace/led-indicator.{sh,service}`)
The 17-LED WS2812 ring (mainline `sun50i-a100-ledc`, `/sys/class/leds/rgb:indicator-{0..16}`)
now lights **green at low brightness on boot** as a "device is on" indicator.

- **Known hardware limitation:** only the **left half** of the ring lights. The
  lit LEDs show the correct colour, so the bit-timing/data path is fine — the
  dead half is a hardware issue (mid-chain break, or the right-half LEDs on a
  segment/rail that is not enabled), not the driver. `led_count = 17` matches the
  vendor DTB. Full-ring fix needs hands-on probing / the board schematic.

## Fan — pinned for fine-tuning
The fan PWM is **inverted** (`PWM_POLARITY_INVERSED`); the fan runs at cooling
state 0 (idle). The mapping direction (hot → more fan) has **not** been verified
on HW yet. Fan-on trip is currently 90 °C; a cooler-running config would start
it earlier (~60-70 °C). Deferred to a dedicated fan-tuning pass.

## Display — root cause found (only-backlight); resume plan

Current state: panel powers up but shows **only backlight**. This is **not** a
regression from the thermal work — the DTB edit added only THS nodes.

Diagnosis: every 2026-09-07 solve ingredient is present on the device —
`use_rcq=1`, `arm_at_target=1`, `a523_stock_trigger=1`, `tcon_curline_phys=0x55020fc`,
and the DTB tcon-top compatible is `allwinner,sun55i-a523-tcon-top`. But the
DSI0/DSI1 clock gate never opens: `set_displl()` (which opens the gate for a523)
**never fires** (no `DSI_GATE=` in the boot log), so `GATE_SRC` stays 0 and the
DSI FIFO stays empty → backlight only.

Root cause: on the build server, the commits **after** the solve commit deleted
~1976 lines from `sun55i_de.c` and ~28 from `sun8i_tcon_top.c`. The deployed
modules were built from that later, **inconsistent** state — `sun8i_tcon_top.ko`
still exports `set_displl`, but the loaded `sun4i_tcon` no longer invokes the
gate. The consistent, HW-proven set lives in the solved commit
(`drm/sun4i: A523 TrimUI Smart Pro S — display bring-up fixes`).
